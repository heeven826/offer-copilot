## 0. 变更一览

v2 → v3 三件事:**传输层升级**(弃 cron、事件驱动)、**文件名寻址**(多 agent 路由)、**读时校验**(坏消息/丢消息防御)。协议层既有原则(单写者/原子写/只追加/回执/稳定 id/erratum)全部保留不动。

## 一、背景

- 现状:两 agent(Claude Code=dev / DeepSeek Harness=dsh)经 `D:\shared_dir\offer-copilot\` 异步协作,v2 已支撑 12 轮反馈闭环
- 调研结论:协议层健全;瓶颈在传输层——dev 侧 2 分钟 cron 每次触发即一次完整模型 turn(8 小时值守约 240 次空转),且每轮追加进会话历史膨胀上下文
- 借鉴:Claude Code agent teams 的信箱亦为文件通信,其"读时校验、发送=写入成功"可移植;拓扑差异见否决记录

### 否决记录(F8 补,防未来翻案重辩)

- **不换 JSON 信箱**:本通道消费者是模型+人;按发送方分目录=单写者免锁,Markdown 信封足够。JSON 是"按收件方信箱"拓扑(N 写者共享文件)的必然选择,与本通道拓扑不匹配
- **不引入消息队列**(Redis/NATS/ZeroMQ):两端 agent 非常驻服务,broker 之后仍需"消息到达→唤醒 turn"的桥,即仍是 watcher;多装一个服务,丢人可读审计
- **不采用 A2A**:要求双方为常驻 HTTP 服务,部署假设不成立;语义上与本协议同构(json块≈Part.data、blocked_on≈input-required)
- **毕业条件**:跨机协作 → A2A 或消息队列;N 增大到需按收件路由 → 按收件方信箱拓扑 + JSON

## 二、传输层([单方]可先行,实施后通报)

**10. dev 侧以"后台 watcher 退出即唤醒"替代 cron。[单方-dev]**
以后台任务运行 until 循环盯 `from-dsh/`(及 v3 后的 `from-watcher/`),有新文件才退出,进程退出通知即唤醒会话;处理消息的 turn 结束时重新拉起(re-arm)。空闲成本为零。
*动机:消除 cron 空转 turn 与上下文污染。*

**11. dsh 侧扫描升级 fs.watch,保留轮询兜底。[单方-dsh]**
本地 NTFS 走 ReadDirectoryChangesW 内核通知,延迟由 ≤60s 降至亚秒;fs.watch 抛错(杀软等边界)时回退 60s 轮询。GitHub HEAD 检查维持 300s 节流不变(网络对端无免费事件,webhook 需公网端点)。
*动机:延迟免费降一个量级,空闲 CPU 归零。*

**12. 读时校验:标记,不删改。[单方,双侧各自实现]**
watcher 对新消息校验:frontmatter 可解析且含 id/from/to/created;正文恰有一个可解析的 ```json 块。不合格 → 唤醒消息附 [格式异常] 标记,由模型发 erratum 请对方补发。**读方不得删除或修改写方目录内的文件。**(F1)**归档(移入 archive/)仅由目录写者执行;读方只能在通道内请求归档。**
*动机:移植 agent teams"读时逐条校验";单写者下"剔除"改写为"标记",保审计链;归档权归写者以消除与 v2 archive 惯例的冲突。*

**13. 序号连续性检测。[单方,双侧各自实现]**
watcher 在**每次事件(或兜底轮询)触发时**(F5),对**对端目录 ∪ archive/ 的文件名序号并集**(F2)排序,发现跳跃(如 0005→0007)即警告"可能丢消息,建议 erratum 查询"。
前提约定(F3):**序号一经分配即消耗,写失败不复用、不回收**——否则空洞无语义。
*动机:dsh 自述的已知风险("写通道需完全权限,消息可能缺失且不静默重试"),现行机制发现不了。*

**附:代码级小修(单方)**
- `channel-poll.mjs` 的 devSeen 数组改为数字高水位 lastSeen,消除 O(n²) 过滤与状态无限增长 [单方-dsh]
- `.state-claude.txt` 迁出 shared_dir 根目录(如 `Boss2/.state/`)——通道目录内只应有消息 [单方-dev]

## 三、协议层(须双方回执确认)

**14. 文件名寻址。**
新消息命名 `NNNN-to-<who>-<topic>.md`,who ∈ {dev, dsh, all, user};发送方身份由所在目录承载(`from-dev/` 即署名),序号仍按目录独立递增。watcher 仅凭 readdir + 文件名即可路由,零文件打开。类型词留在 topic 槽,如 `0015-to-dsh-ack-0013.md`(F9)。
**适用边界(F4)**:本方案在"同一台机器、个位数 agent"区间内成立;跨机或大 N 时按否决记录的毕业条件迁移。
*动机:"信封即路径"——目录名编码 from、文件名编码 to。*

**15. 双权威:文件名=路由权威,frontmatter=内容权威。**
二者不一致(文件名 to-dsh 而 frontmatter `to: dev`)按坏消息处理,走 erratum。
*动机:同一事实两处存放必然漂移(节奏数值一日内即漂移过),须指定唯一裁决源。*

**16. frontmatter 增加 kind 字段。**
kind ∈ {finding, ack, notice, erratum},与现有 status 并行,将目前藏在文件名里的类型信息显式化。**仅对 v3 生效后的新消息强制,存量消息豁免**(F6);枚举是否补充 handshake/misc 待 dsh 确认。
*动机:为 watcher 未来按类型分流预留钩子(如 ack 类只记不唤醒)。*

**17. to-all 广播与 to-user 用户裁决。**
to-all 为广播信,各方 watcher 均可唤醒;to-user 对接规矩 9(分歧升级),**各方 watcher 对对端目录中的 to-user 信负责**(F7),检测到时在唤醒消息加显眼标记(如 [需要你裁决])。
*动机:让人类这个"终极 agent"拥有收件地址,升级路径从约定落为机制。*

**18. 全员可读,按址唤醒;路由≠访问控制。**
任何一方可读通道内全部消息(审计权不变);唤醒优先级按 to 决定:to-我 → 立即唤醒;to-他人 → 不唤醒(或仅一行摘要)但可查。禁止将寻址做成访问控制。
*动机:审计链是本通道核心资产,路由只能影响唤醒,不能限制读取。*

**19. archive 自描述。**
消息移入 `archive/` 后脱离原目录即丢失目录承载的 from;归档文件以 frontmatter 的 from 字段辨识来源,文件名中的 to 保持不变。(可选:归档时文件名补 from- 段 [设想])
*动机:归档消息离开原目录后仍须独立可读。*

**20. 对外单声。**
任一侧内部再拉子团队(如 dev 侧用 agent teams)时,对外出站目录的写者必须仍只有 lead 一人;内部协调走该 harness 内部机制,不经本通道。
*动机:保持对外单写者不变,两层协作互不污染。*

**21. 机制与数值分离(修订 v2「节奏」一节)。**
PROTOCOL.md 只写机制(唤醒方式、变更流程、谁须通报);当前数值(间隔、上限、冷却)只记录于 STATUS.md,由现行"谁变更谁更新"规矩管辖。
*动机:v2 节奏一节一日内即与现实漂移(写 10/20 分钟,实际 2 分钟 cron 与 60s+300s)。*
